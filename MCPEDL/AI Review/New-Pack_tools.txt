# mcpe-context7: Where to Look Things Up

## Authority

- `INSTRUCTIONS.md` 1.16 (copy in `docs/instructions-reference.md`) is the policy. This skill is only its routing table and never overrides it.
- An AI review kit (`*_tools.txt`) holds a directory map and skills, no file contents. That is on purpose: read what the task needs through Context7, not from a pasted dump.

## Libraries (ONLY these four, IDs exactly, `query-docs` only)

- `/microsoftdocs/minecraft-creator`: `@minecraft/server` and `@minecraft/server-ui` API, JSON schemas, stable and module versions.
- `/mojang/bedrock-samples`: vanilla ids, textures, recipes, components, entities, formats, `version.json`.
- `/websites/wiki_bedrock_dev`: manifest structure, scripting guides, techniques.
- `/allenscreations/mcpe-curseforges`: this repo's rules, script summaries and Bedrock guide. Context7 indexes ONLY `docs/`.

NEVER call `resolve-library-id`. NEVER query any other library.

## Repo lookups (`/allenscreations/mcpe-curseforges`, `docs/` only)

- `docs/instructions-reference.md`: `INSTRUCTIONS.md`, `DOCS_RULES.md`, `PACK_GENERATOR_INSTRUCTIONS.md` (Reply Format, Termux Script Rules, versions 1.3, recipes 1.4 and 1.5, templates 2.5, new packs Part 4).
- `docs/scripts-and-workflows.md`: summary of every script and workflow, update spec syntax (`apply_update.py`, `make_update_script.py`).
- `docs/bedrock-guide.md`: add-on architecture, folder structure, manifest setup, target API versions.
- Meaning of a build or doc check message: query the exact message text with the script name.

## Rules

1. Query first, write second. Batch: at most ONE `query-docs` call per needed `libraryId`, covering every topic needed from it, all calls in one parallel turn. NEVER two calls to the same `libraryId`. Name the exact member, file, id or schema and the game or module version.
2. Verify every import, class, method, property and JSON field against the retrieved text. NEVER `mojang-minecraft`, `world.events` or 1.x syntax.
3. Empty or doubtful result: no sequential retry loop. Say "not verified". NEVER fill the gap from memory.
4. Versions come only from retrieved text. State the exact version used and the query date.
5. Handoff bullet: `Docs queried (YYYY-MM-DD): <library IDs and topics>`.
6. Library IDs, query text and the word Context7 NEVER go into shipped files or player-facing docs.

## Scripts that must run

- `make_pack_script.py`, `build_payload.py`, `import_project_payload.py`, `doc_template.py`, `pixel_json_to_png.py`, `make_update_script.py` and `apply_update.py` need their COMPLETE unchanged text. A Context7 snippet is not enough.
- The complete files are in the kit zip (`New-Pack_files.zip`, `Update-Pack_files.zip` or `tools_files.zip`) under `files/`. Unzip, run from there, NEVER retype or edit them.
- No zip and only partial text from a query: stop and ask the user to attach the zip. NEVER rewrite a script from memory.
- A file attached in the conversation or read from a clone wins over the Context7 index. Context7 shows the repo as last indexed. Tell the user about any difference.

## Reading the directory map

- NEVER edit generated folders and files: `builds/`, `Package/`, `changelog_views/`, `MCPEDL/AI Review/`, `MCPEDL/README.md`, `builds/README.md`.

# mcpe-new-pack: Build a New Pack

## Authority

- This skill is the entry point and a checklist. It never restates or overrides policy. The rules live in `PACK_GENERATOR_INSTRUCTIONS.md` (Part 4), `INSTRUCTIONS.md` and `DOCS_RULES.md`. On any conflict `INSTRUCTIONS.md` wins, then `DOCS_RULES.md`, then the generator file.
- The complete scripts below are in `New-Pack_files.zip` under `files/`: unzip and run them, never retype them. Everything else is read through Context7 (`mcpe-context7` skill); `New-Pack_tools.txt` holds only a directory map and the skills.
- If a required file cannot be read, stop and say which one. NEVER work from memory or from an old copy.
- Updating an existing pack is a different job: use the `mcpe-pack-update` skill and `INSTRUCTIONS.md` "Termux Script Rules".

## Do these in order

1. **Read first, then build.** `INSTRUCTIONS.md` (Reply Format, Termux Script Rules, 1.1 to 1.4, 1.7, 1.12), then `DOCS_RULES.md` (2.1 to 2.5), then ALL of `PACK_GENERATOR_INSTRUCTIONS.md`. Read through Context7 (INSTRUCTIONS.md 1.16: four fixed libraries, `query-docs` only; an attached `tools.txt` wins on any difference). Then read the scripts that decide what passes: `scripts/build_payload.py`, `scripts/doc_template.py`, `scripts/import_project_payload.py`, `scripts/make_pack_script.py` (plus `scripts/pixel_json_to_png.py` when drawing textures).
2. **Type.** If the user did not say addon, map, script or minigame, ask the exact question in 4.0 and wait. NEVER guess.
3. **Look up** with Context7 `query-docs` (`/microsoftdocs/minecraft-creator`, `/mojang/bedrock-samples`, `/websites/wiki_bedrock_dev`) the latest stable Bedrock release and `@minecraft/server` / `@minecraft/server-ui` versions now, and verify every API member and JSON field before using it. Record the date. NEVER use numbers from memory or from this repo's old packs.
4. **Build** the project in scratch `build/<Name>/` using the 4.2 layout. Fresh v4 UUIDs for every header and module. Write the BP manifest (with the looked-up `min_engine_version`) BEFORE running the script.
5. **Run `scripts/make_pack_script.py build/<Name>`.** Fix every failure, including every `DOC:` line, and rerun until SELF-TEST PASSED, PACK SCRIPT OK and BUILD OK print. Then `python3 doc_template.py --style build/<Name>`, rewrite every STYLE hint with a specific fact, rebuild.
6. **Deliver** exactly ONE file: `<Name>_<Version>_<Rand>.sh`. Reply in the three sections of 4.11 and nothing else.

## Most often missed

- NEVER write base64, a ZIP or the `.sh` by hand. NEVER hand-edit the `.sh`. Cannot run code: reply `CANNOT BUILD`.
- No other deliverable: no `.zip`, `.mcaddon`, `.mcworld`, `.mcpack`, `.json`, `.js`, `.b64`. `build/` is scratch and is never delivered.
- There is no test world. NEVER ship `test_world.json` (the build rejects it) and NEVER promise a `- Test.mcworld`.
- The importer creates `assets/snapshots`, `assets/recipes` and `assets/items` for the pack. NEVER ship `assets/`, `Mcpeworlds/` or listing images in the payload.
- Every custom crafting recipe needs `AlwaysUnlocked` (1.4). Every custom recipe and item shown in DESCRIPTION gets its image from `scripts/generate_recipe_images.py` after import (1.5).
- Docs follow the templates in `DOCS_RULES.md` 2.5 exactly: README is the 11-line download landing page, DESCRIPTION has the exact section order, both badges and both listing images, and says `not tested in game`, the achievement status and the experiments status.
- No comments in `.js`, `.mcfunction` or `.json`. Versions are `X.Y.Z` only. `by ALNStudios` appears once per description, never in a name.
- Map: `void_cleaner` first in `tick.json`, exact fill line, conditional `void_cleaned` tag, Trader Ledger from the repo copy. Minigame: Controller from the repo copy (it already is the ALN UI Redesign menu: never edit or replace it), `registerController` with `title`, `version` equal to the BP manifest, `about`, real `gameInfo` and `howToPlay` with no color codes, real logic that calls `endGame()`. NEVER build your own form. Script: Behavior Pack only, `.mcpack`.
- Never claim anything was tested in Minecraft. The checks prove structure only.

## After the pack is in the repo

- Register the CurseForge project ID with the **Register CurseForge ID** workflow. It saves the ID, refreshes the publish dropdown and then starts **Build Changed Packs & Sync Catalogs** by itself. Nothing else needs to be run by hand.
- Versions never change on a build. Only an update script or **Publish to CurseForge** moves them.
